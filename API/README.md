## 📌 О проекте

Тестирование новой функциональности бэкенда **Яндекс.Прилавка**. Разработчики добавили работу с наборами, расчёт доставки курьерской службой и работу с корзиной. Новую версию API передали на тестирование перед выпуском.

**Объект тестирования:** REST API Яндекс.Прилавка.
**Тестовые ручки:**

- `POST /api/v1/kits/{id}/products` — добавление продуктов в набор;
- `POST /fast-delivery/v3.1.1/calculate-delivery.xml` — расчёт доставки курьерской службой «Привезём быстро»;
- `GET /api/v1/orders/{id}` — получение содержимого корзины;
- `PUT /api/v1/orders/{id}` — добавление продуктов в корзину;
- `DELETE /api/v1/orders/{id}` — удаление корзины.

**Инструмент тестирования:** Postman.
**Форматы данных:** JSON, XML.

## 🐞 Ключевые дефекты

- **БР46 (критический)** — `DELETE /api/v1/orders/{id}`: только что созданная корзина не удаляется. Ответ 404 Not Found вместо 200. Блокирует базовый пользовательский сценарий.
- **БР1, БР3, БР4, БР5 (высокий)** — сервер возвращает 500 Internal Server Error в формате HTML вместо 400 Bad Request при невалидных значениях `id` продукта. Ошибки сервера вместо валидации.
- **БР2 (высокий)** — нет валидации `id` продукта: сервер принимает 200 OK для несуществующего, отрицательного, нулевого, `null` и отсутствующего `id`.
- **БР10–БР17 (высокий)** — нет валидации `quantity` и структуры `productsList`: сервер принимает `quantity=0`, `-1`, `null`, пустой массив, `null`, пустое тело без ошибки.
- **БР18–БР30, БР50 (высокий)** — ручка курьера принимает любые значения `productsCount`, `productsWeight`, `deliveryTime` без ошибки. При отсутствии параметра — 500 вместо 400.
- **БР32–БР37 (высокий)** — `PUT /api/v1/orders/{id}` возвращает 409 Conflict вместо 400 Bad Request при невалидных `id` продукта.

## 💡 Вывод и рекомендации

**Версию API к выпуску не рекомендую.** Выявлен 1 критический дефект и 41 высокоприоритетная проблема. В совокупности они делают систему непригодной для использования:

- ключевая функция — удаление корзины — не работает;
- отсутствует валидация числовых параметров и структуры тела запроса;
- сервер отвечает 500 в формате HTML вместо 400 с JSON при невалидных данных;
- некорректные HTTP-коды (409 вместо 400) вводят в заблуждение.

**Приоритеты по исправлению:**

1. Немедленно — критический **БР46** (удаление корзины).
2. Реализовать единый слой валидации для всех числовых параметров: тип, диапазон, обязательность. Невалидные запросы — код 400 с понятным JSON-сообщением.
3. Унифицировать формат ответов об ошибках — всегда JSON.
4. Настроить очистку контекста между запросами: замечено накопление мусорных значений `quantity`.
5. После исправления — повторное регрессионное тестирование.

## 🛠 Использованные подходы и виды тестирования

- **Функциональное тестирование API** через Postman.
- **Тест-дизайн:**
  - классы эквивалентности (позитивные и негативные);
  - граничные значения (диапазоны `quantity`, `productsCount`, `productsWeight`, `deliveryTime`);
  - невалидные типы данных (буквы, спецсимволы, дроби);
  - отсутствие параметра, `null`, пустой массив, пустое тело.
- **Исследовательское тестирование** с анализом серверных логов для подтверждения дефектов.
- **Работа с серверными логами:** логи по `/fast-delivery/...` получены через `/api/logs/main` и `/api/logs/secondary`.
